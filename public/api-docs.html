סקירה

ה-API מאפשר למערכות אחרות ליצור בקשות חופש מידע, לעדכן כל אחד מהשדות שלהן ולקרוא אותן, בלי להיכנס לפורטל. הבקשות נשמרות בסיילספורס (Case מסוג ״בקשה״), בדיוק כמו בקשה שנפתחה בפורטל, ואותם כללי תקינות חלים עליהן: שדות חובה, ערכים מתוך הרשימה, מטפל/ת שהוא/היא משתמש/ת פורטל וכן הלאה.

  • כתובת הבסיס: https://<השרת>/api/v1
  • פורמט: JSON ב-UTF-8, בבקשה ובתשובה. בבקשות POST ו-PATCH יש לשלוח Content-Type: application/json.
  • תאריכים: YYYY-MM-DD לשדה תאריך, ו-ISO 8601 (למשל 2026-11-12T09:30:00Z) לתאריך ושעה.
  • מה אי אפשר: למחוק בקשות, להוסיף עדכוני פעילות או קבצים, ולנהל משתמשים וקבוצות. אלה נעשים רק בפורטל.

אימות: הטוקן המשותף

כל קריאה חייבת לכלול טוקן בכותרת Authorization:

Authorization: Bearer <API_TOKEN>
X-Client-Name: my-system        (רשות, מומלץ)
  • הטוקן שמור על השרת בלבד, כסוד (secret) בשם API_TOKEN בהגדרות האפליקציה. הוא משותף לפורטל ולמערכות שמזינות אליו מידע: מי שצריך/ה לדחוף מידע מקבל/ת אותו מאדמין המערכת, בערוץ מאובטח.
  • הטוקן חייב להיות באורך 24 תווים לפחות (מומלץ 40 ומעלה, אקראי, למשל openssl rand -hex 32). כשאין טוקן מוגדר, ה-API כבוי ומחזיר 503.
  • החלפת טוקן בלי הפסקת שירות: אפשר להגדיר כמה טוקנים מופרדים בפסיק (API_TOKEN=new,old). אחרי שכל המערכות עברו לחדש, מסירים את הישן.
  • X-Client-Name הוא שם המערכת הקוראת (אותיות לטיניות, ספרות, נקודה, מקף וקו תחתון, עד 40 תווים). הוא מופיע ביומנים כ-api:<שם>, כדי שיהיה ברור מי עשה מה. בלי הכותרת הקריאה נרשמת כ-api:client.
  • הטוקן מעניק הרשאה של אדמין על בקשות המידע בכל הלוחות. יש לשמור אותו רק בצד השרת של המערכת הקוראת, לא בקוד שרץ בדפדפן, לא באפליקציה ולא במאגר קוד. ה-API לא מאפשר קריאות מדפדפן של אתר אחר (אין CORS).
  • טוקן חסר או שגוי מחזיר 401. אחרי 20 ניסיונות שגויים מאותה כתובת IP בתוך 10 דקות, הכתובת נחסמת (429) עד סוף החלון.

רישום ביומנים

  • יומן הגישה: כל קריאה ל-API נרשמת, כולל קריאות קריאה בלבד וניסיונות עם טוקן חסר או שגוי: מתי, שם המערכת (api:<שם>), הפעולה, הבקשה שבה נגעה הקריאה, התוצאה, כתובת IP וה-User Agent. גוף הבקשה והטוקן לא נרשמים. האדמינים רואים את זה ב״יומן גישה״ בפורטל.
  • יומן העריכות: כל יצירה ועדכון דרך ה-API נרשמים שדה אחרי שדה (מה היה ומה נהיה), וגם מופיעים בהיסטוריה של הבקשה בפורטל, בשם api:<שם>.

איך שולחים ערכים לשדות

השדות נשלחים באובייקט fields, לפי שם ה-API של השדה (למשל request_name__c), לא לפי התווית בעברית. הסוג של כל שדה מופיע ברשימת השדות.

סוגמה לשלוחדוגמה
string, textarea, urlמחרוזת, עד האורך המותר"בקשה לפרוטוקולים"
dateמחרוזת YYYY-MM-DD"2026-11-12"
datetimeISO 8601"2026-11-12T09:30:00+02:00"
booleantrue / falsetrue
double, int, currency, percentמספר120
picklistאחד מהערכים (value, לא התווית) שברשימה של השדה"New"
multipicklistמערך של ערכים, או מחרוזת מופרדת ב-;["a", "b"]
reference (שדה בחירה)מזהה סיילספורס, או אובייקט שמזהה את הרשומה (ראו למטה)"001AB00000abcdeXYZ"
כל סוגnull או "" מרוקנים את השדה (לא בשדות חובה)null

שדות בחירה (reference)

במקום מזהה סיילספורס אפשר לשלוח אובייקט, והשרת מוצא את הרשומה:

שדהמצביע עלאובייקט במקום מזהה
request_org_name__cגוף ציבורי (Account){"name": "משרד הבריאות"} – שם מדויק; אם יש יותר מאחד, צריך לשלוח מזהה
request_initiator__cיוזם/ת הבקשה (Contact){"email": "person@example.org"} – איש קשר קיים עם המייל הזה
metapel_bakasha__cהמטפל/ת בבקשה (משתמש/ת פורטל){"email": "student@example.ac.il"} – משתמש/ת רשום/ה בפורטל

ה-API לא יוצר גופים ציבוריים או אנשי קשר חדשים. כדי למצוא מזהים, השתמשו ב-GET /lookup.

שדות שאינם ברשימה, או שאי אפשר למלא או לעדכן (למשל CaseNumber, OwnerId), נדחים עם שגיאה unknown_fields, כדי ששגיאת כתיב בשם שדה לא תעבור בשקט.

לוחות ובעלות על בקשה

כל בקשה שייכת ללוח של קבוצה: קליניקה, או ״עובדי התנועה״. הלוח נקבע לפי הבעלים (Owner) של הבקשה בסיילספורס, וכך גם ב-API:

  • לוח של קליניקה: הבקשה משויכת למשתמש הסיילספורס של הקליניקה. אין צורך לשלוח בעלים.
  • לוח עובדי התנועה: חובה לשלוח owner_email: המייל של עובד/ת התנועה שהבקשה תהיה שלו/ה. השרת משתמש במשתמש הסיילספורס ששויך לו/ה בפורטל, ואם אין, במשתמש סיילספורס פעיל עם אותו מייל.

את הלוחות ומזהיהם מקבלים ב-GET /boards. אפשר לשלוח את board כמזהה (מספר) או כשם המדויק של הלוח.

נקודות הקצה

כל הנתיבים יחסיים לכתובת הבסיס /api/v1. בקשה מזוהה בנתיב (:key) לפי מזהה הסיילספורס שלה (15 או 18 תווים) או לפי מספר הבקשה (00012345 או 12345).

GET /ping

בדיקה שהטוקן תקין. לא נוגע בסיילספורס.

200 {"ok": true, "client": "api:my-system"}

GET /fields

כל השדות שאפשר להזין, לפי מקטעי הטופס: שם, תווית, סוג, חובה, אורך מרבי, הסבר, אם אפשר למלא ביצירה (createable) ובעדכון (updateable), ובשדות רשימה – הערכים המותרים. הנתונים נלקחים מסיילספורס, ולכן תמיד מעודכנים.

GET /boards

הלוחות (קבוצות). ownerRequired: true פירושו שביצירה בלוח הזה חובה לשלוח owner_email.

200 {
  "boards": [
    { "id": 1, "name": "עובדי התנועה", "kind": "staff", "owner": null, "ownerRequired": true },
    { "id": 2, "name": "המרכז הבינתחומי", "kind": "clinic",
      "owner": { "id": "0051n000004X6q1AAC", "name": "המרכז הבינתחומי" }, "ownerRequired": false }
  ]
}

GET /lookup/{Account|Contact|handler}?q=

מציאת מזהים לשדות בחירה. Account – גופים ציבוריים, Contact – אנשי קשר (יוזמי בקשות), לפי חלק מהשם; ל-Account ול-Contact חובה q באורך 2 תווים לפחות, ומוחזרות עד 50 תוצאות. handler – משתמשי הפורטל שאפשר לבחור כמטפלים, עם המייל והקבוצה; q רשות.

GET /lookup/Account?q=בריאות
200 {"records": [ {"id": "001…", "name": "משרד הבריאות"} ]}

GET /lookup/handler?q=dana
200 {"records": [ {"id": "003…", "name": "דנה כהן", "email": "dana@example.ac.il", "group": "המכללה למנהל"} ]}

GET /requests

חיפוש בקשות, מהעדכנית לישנה. כל הפרמטרים רשות ואפשר לשלב ביניהם:

POST /requests

יצירת בקשה. גוף הבקשה:

  • board (חובה) – מזהה או שם של לוח.
  • owner_email – חובה בלוח עובדי התנועה בלבד (ראו לוחות ובעלות).
  • fields (חובה) – ערכי השדות. כל שדות החובה (מסומנים ברשימה) חייבים להופיע.
POST /requests
{
  "board": "המרכז הבינתחומי",
  "fields": {
    "request_name__c": "פרוטוקולי ועדת המכרזים 2025",
    "Description": "בקשה לקבלת כל הפרוטוקולים של ועדת המכרזים בשנת 2025",
    "Status": "New",
    "request_date__c": "2026-11-12",
    "request_org_name__c": { "name": "משרד הבריאות" },
    "request_initiator__c": { "email": "person@example.org" },
    "metapel_bakasha__c": { "email": "student@example.ac.il" },
    "Origin": "Web"
  }
}

201 { "id": "500…", "caseNumber": "00012346",
      "board": { "id": 2, "name": "המרכז הבינתחומי", "kind": "clinic" },
      "ownerName": "המרכז הבינתחומי", "lastModified": "2026-11-12T09:30:00.000+0000" }

הערכים "New" ו-"Web" הם דוגמה. הערכים האמיתיים של כל רשימה מופיעים ב-GET /fields ובטבלה למטה.

PATCH /requests/:key

עדכון חלק מהשדות או כולם. נשלחים רק השדות שרוצים לשנות; שדה שערכו זהה לקיים לא נחשב שינוי. אפשר לצרף lastModified כפי שהתקבל בקריאה הקודמת, ואז אם מישהו שינה את הבקשה בינתיים העדכון נדחה ב-409 ולא דורס את השינוי שלו.

PATCH /requests/00012346
{
  "lastModified": "2026-11-12T09:30:00.000+0000",
  "fields": {
    "Status": "Answered",
    "first_Answerd__c": "2026-12-01",
    "Answer__c": "התקבלו הפרוטוקולים במלואם"
  }
}

200 { "ok": true, "id": "500…", "caseNumber": "00012346",
      "changed": ["Status", "first_Answerd__c", "Answer__c"],
      "lastModified": "2026-12-01T10:00:00.000+0000" }

שגיאות

כל שגיאה מוחזרת כ-JSON עם קוד קבוע ב-error והסבר בעברית ב-message. בשגיאות תקינות יש גם errors (רשימה), ולפעמים missing או fields עם שמות השדות.

400 { "error": "invalid", "message": "שדות חובה חסרים: Origin; סטטוס: ערך לא ברשימה",
      "errors": ["שדות חובה חסרים: Origin", "סטטוס: ערך לא ברשימה"], "missing": ["Origin"] }
סטטוסerrorמתי
400invalidשדות חובה חסרים, ערך לא תקין או לא ברשימה, שדה בחירה שלא נמצא
400unknown_fieldsשם שדה לא מוכר, או שדה שאי אפשר למלא או לעדכן
400bad_board, owner_required, owner_not_foundלוח לא נמצא; חסר owner_email בלוח עובדי התנועה; לא נמצא לו משתמש סיילספורס
400bad_handlerהמטפל/ת אינו/ה משתמש/ת רשום/ה בפורטל
400bad_request, bad_jsonסיילספורס דחה את השמירה (ההסבר ב-message); גוף שאינו JSON תקין
401no_token, bad_tokenאין טוקן, או שהטוקן שגוי
404not_found, no_such_endpointהבקשה לא נמצאה; נתיב לא קיים
409conflictהבקשה השתנתה אחרי lastModified שנשלח. התשובה כוללת את הערך העדכני
413too_largeגוף הבקשה גדול מ-1MB
429too_many_attemptsיותר מדי ניסיונות עם טוקן שגוי מאותה כתובת
500server_errorתקלה בשרת או בחיבור לסיילספורס. אפשר לנסות שוב מאוחר יותר
503api_disabledלא הוגדר API_TOKEN בשרת

מגבלות

  • גוף בקשה עד 1MB. בקשה אחת בכל קריאה (אין יצירה מרובה); לייבוא גדול, שלחו בזו אחר זו.
  • סיילספורס מגביל את מספר קריאות ה-API ביום לכל הארגון, והפורטל משתמש באותה מכסה. כל יצירה צורכת כמה קריאות. לסנכרון, העדיפו modifiedSince על פני קריאה של כל הבקשות.
  • לפני יצירה כדאי לבדוק אם הבקשה כבר קיימת (למשל GET /requests?asmahta=…), כי ה-API לא מונע כפילויות.
